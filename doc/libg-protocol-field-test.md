## libg 实际协议路径追加观察（2026-10-23）

用户确认：在原始 IDB 中用 IDA 也看不到 socket/connect/recvfrom/sendto 等导入的直接 xref，因此本次不把“导出器没有 xref”列为已确认缺陷。它是输入分析状态或导入链未解析的未决数据质量问题；工具应把“没有找到”与“确认无调用”分开显示。

本轮从消息虚表、工厂和收发路径得到以下可复核事实：

- 以 `+0x30 == 0x12282E8` 为非零锚点，并要求七个函数槽为已知入口，内存扫描得到 348 个候选；其中 341 张表有可解析的常量消息号 getter，340 个不同消息号。候选不是运行时可达消息全集。
- 发送路径 `0x1392AE0` 先调用消息编码，再通过 `0x121E814` 得到编码长度；写入 7 字节头：消息号 2 字节大端、长度 3 字节大端、对象 `+0x88` 的版本低 16 位大端。长度上限检查为 `< 0x1000000`。转换器和 IO 发送均为虚调用。
- 接收路径先读取 7 字节头；回调按同样的 2/3/2 宽度解析，再读取负载、经过转换器、由消息工厂按消息号构造对象，写入版本并调用解码。当前转换器在构造时是零开销复制实现，但握手路径通过 `0x1393CE4` 安装另一个转换器，不能据此断言整个连接无加密。
- `0x1228354` 读取对象 `+0x88`，`0x122835C` 写入它；因此消息虚表 `+0x20` 的常量（例如 11）不能解释为线上的版本字段。`15687` 的工厂分支直接构造已知聊天消息对象。
- 共享跳转器的静态解析已重放 97 个调用；其结果保存在实验目录的派生 JSON，没有把伪造 xref 写回 IDB。`0x1393990` 的关键转换器调用、`0x1393278` 的消息构造/解码调用均可解析；其中一个解析目标落在 `0x1393594`；IDB 的函数块探针显示它属于 `0x1393278` 的同一入口范围，而不是独立函数入口。

本轮实际暴露的工作流问题：

- **GAP-007（实际遇到，性能）**：向 CLI 传入 683 个离散地址时，选择器在启动 IDA 前对全库 70,033 个函数反复扫描，最终取消；用已核验的 SQLite 地址直接调用内部 batch runner 后，683 个汇编视图约 3.859 秒完成。需要让显式地址选择一次建索引，避免 preview/final 重复全库扫描。
- **GAP-008（实际遇到，输出放大）**：读取 160,000 字节同时返回十六进制字符串和整数数组，控制台输出约 485k token 级别。数据读取能力本身可用，但应提供摘要/流式文件/仅 hex 或仅数组选项，避免 AI 上下文被结果格式耗尽。
- **GAP-009（实际遇到，派生证据）**：共享跳转器解析对协议路径很有用，但当前结果只在本地 JSON，不能作为带来源、调用 EA、解析方法和置信度的 SQL 证据/导航关系。需要独立的 derived-call 表或统一 evidence graph，并明确它不等同于 IDA 原生 xref。
- **GAP-010（实际遇到，输入边界）**：`0x1393278` 伪代码把接收分发逻辑和一段冷/备用控制流合在一个很大的入口范围内，出现未初始化局部变量与不自然分支；函数块探针确认 `0x1393594` 属于该函数范围，不能称为独立共享尾。工具仍应暴露 function chunk、冷块/备用块和反编译可靠性警告，不能把反编译文本当成完整可靠函数语义。

这些问题均未通过修改目标 IDB 或伪造 xref 规避；报告与原始日志留在被忽略的实验目录。

## 握手转换器与新增边界

继续分析握手替换的转换器后，确认其核心槽位是转发层。发送路径 `0x1A2BD10` 从转换器 `+0x20` 取出依赖对象，调用该对象虚表 `+0x18`，并返回状态取反；接收路径 `0x17E5600` 使用 TLS 和一个全局对象，先调用虚表 `+0x740`，再按状态 1/2/3 选择 `+0xB0`、`+0xB8` 或 `+0x718`。这些行为足以否定“握手后仍是简单复制”，但不足以命名具体加密或压缩算法。

两个关键静态值在当前 IDB 中都不是已映射镜像指针，辅助 fixup 查询也没有记录；因此具体依赖实现留为未决。相关 job 已新增 hypothesis/reject 边界及问题，不把外部 ABI 名称或壳外推测写进事实。

## 消息序列化、JNI 边界与共享分派

消息基类构造 `0x12282A8` 在对象 `+8` 构造流对象，并把流表设为 `0x18CB288`。该表给出的关键契约是：

- `+0x50 -> 0x121F184`：编码一个 32 位值；最终 `0x121E960` 以最高有效字节优先写出，因此为 **大端 32 位**。
- `+0xF0 -> 0x121F53C`：从流读取 **大端 32 位**。
- `+0x20 -> 0x121E854`：编码 `std::string`，以 32 位长度前缀后接原始字节；超过 900,000 字节时写 `-1`。
- `+0x70 -> 0x121F7B8`：编码任意字节区，以 32 位长度前缀后接数据；空指针写 `-1`。
- `0x1227064/0x12270A8`：分别连续写/读两个 32 位值。

基于以上契约，静态可验证的消息布局为：

| 消息 ID | 已恢复的负载布局 | 证据边界 |
| --- | --- | --- |
| `15687` | `u32be @ +0x90`, `u32be @ +0x94` | 编解码都走 `0x1227064/0x12270A8`；业务语义未确定 |
| `20100` | `bytes{ptr @ +0x90, len @ +0x98}`，带 32 位长度前缀，空值为 `-1` | 编解码直接调用 `0x121F7B8` 和相应读取路径；未命名字节内容 |
| `10100` | 顺序为 7 个 32 位写槽 `+0x90,+0x94,+0x98,+0x9C,+0xA0,+0xB8,+0xBC`、字符串 `+0xA8`、字节区 `{ptr +0xC0,len +0xC8}` | 四个整数写槽直接落到 `0x121F184`；其余三个整数槽经过共享分派桩，不能从伪代码确认函数身份；字符串和字节区直接可证 |

消息代码中高频出现的 `sub_1A324D8` 并非普通业务函数：它保存多组参数和状态，根据返回地址参与查表分派，当前静态数据库把 6,609 个调用点都折叠到这个目标。部分解码槽因此只得到未初始化的 `v2/v3/...`，不能把伪代码中的路径当作完整调用语义。这里记录为 **GAP-012：共享分派造成调用目标/返回值归属丢失**。不能把折叠后的调用边误当成所有调用点实际执行同一函数，也不能据此推断具体字段类型。

握手变换的关键全局也已恢复到来源层：`JNI_OnLoad` 调用 `0x17E54AC(vm)` 初始化 `qword_1A23D20`；后续代码通过它取得 JNI 环境，使用 `getClassLoader/loadClass` 加载 `com/sistr/safejni/NativeProxy`。因此 `0x17E5600` 的虚方法选择和 `0x17E57D0` 的 Java 反射路径属于 **JNI 边界**。静态库能确认握手安装了非复制的变换入口，具体算法实现可能在 Java/运行时对象中；没有证据时不得命名为 AES、RC4 或其他算法。

新导出的 `crypto_error_*` 字符串位于 `0xAE3C5C` 的错误/遥测路径，只表示 inbound/outbound/loop 错误统计，不是算法常量的证据。
