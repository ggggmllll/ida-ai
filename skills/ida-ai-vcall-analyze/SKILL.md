---
name: ida-ai-vcall-analyze
description: Resolve a stored indirect-call pattern against compatible indexed slots without asserting dynamic reachability.
---

```text
python -m ida_ai vcall-analyze --db ANALYSIS.sqlite --call-id VCALL...
python -m ida_ai vcall-analyze --db ANALYSIS.sqlite --address ADDRESS
```

The call address must be indexed by `vcall-build`. Only a complete supported chain with a usable receiver-argument identity is indexed as `vtable_pattern_candidate`; missing, mismatched or ambiguous argument binding remains `indirect_unknown` and has no target resolution. Supported chains include a direct receiver → vptr → constant slot sequence and a loaded-pointer receiver sequence where an exact pointer loaded from a constant-offset field is passed as the receiver before its vptr and slot loads. The loaded pointer's field offset is distinct from the receiver-relative vptr offset. Unknown sites include an `evidence.unknown_reason.code` triage label such as `call_operand_tree_truncated`, `function_operand_tree_truncated`, `multiple_cross_block_definitions`, `cfg_incomplete`, `receiver_binding_failed`, or `indirect_call_shape_unresolved`; these labels guide follow-up exports and are not semantic proofs. For a complete supported chain, the tool matches the recorded slot byte offset and pointer width against current `vtable_slots`. It also checks current function-local vptr stores for exact object identity/offset and same-block prior order or a dominating block. Matching stores become `prior_vptr_writes` evidence and are linked in `receiver_flows`; compatible table targets record whether an exact candidate table was observed at such a store. The tool stores candidate target rows for inspection.

`candidate_set` means indexed slots are structurally compatible. Read `resolution.candidate_counts` for compatible table-slot rows, distinct target EAs, and the prior-store-narrowed counts; these are counts, never probabilities. A matched prior store is still only a candidate: aliases, intervening writes, calls, object lifetime and construction phases are not proven. `unknown` means the call pattern or receiver binding is incomplete, or no compatible slot is indexed. Candidate rows preserve slot entry classifications such as nullstub, thunk, and IDA library-function flags; the library flag does not imply a dynamic import. Runtime-stub labels come from symbol names only. The result is always `partial` at this stage: the matched argument's ABI role, receiver-to-table reachability, dynamic type, external modules, and unindexed tables remain unknown. Treat `target_ea` and thunk links as candidates, not confirmed call targets. Review `receiver_binding`, `prior_vptr_writes`, the definition chain and unknown frontier before recording a job claim.

`resolution.local_memory` separately queries reaching stores at the vptr load, checking overwrite, partial overlap, potential alias and call barriers. Targets carry `matching_reaching_store_candidate`; `memory_supported_table_slot_rows` counts those matches. The older `prior_store_narrowed_*` fields are retained as historical prior-store counts only (`prior_store_counts_are_historical_only: true`), not surviving-store proofs. For bounded LVARS caller/return tracing and immutable, job-addressable results use `vcall-trace`. Thunk chains and adjustment uncertainty are preserved per target.
